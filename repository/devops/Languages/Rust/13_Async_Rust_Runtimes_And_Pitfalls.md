# Async Rust: runtimes and pitfalls

[← Back to Rust](./README.md)

## What this chapter covers

What **`async` / `await`** means in the language, how the **`Future`** trait fits, why **async is not multithreading by itself**, why you need a **runtime**, common pitfalls (**blocking**, **cancellation**, **`Pin`** at a high level), and when to **stay synchronous**. After this chapter you should choose async only when concurrency of many waits justifies the model—and review async code for scheduler assumptions.

---

## 1. Concepts

### 1. `async` / `await` as a language feature

An **`async fn`** (or `async` block) transforms into a type that implements **`Future`**. The function body does not run to completion when called; it returns a future you must **poll** (usually by awaiting it on an executor).

```rust
async fn fetch_status() -> u16 {
    // await points yield control when the operation is not ready
    200
}
```

**`await`** suspends the current future until the awaited future completes, allowing the executor to run other ready work on that thread. Suspension is cooperative: progress happens when futures are polled again after readiness.

### 2. The `Future` trait (conceptual)

A **`Future`** represents a value that may not be ready yet. The core operation is **poll**: given a context (including a waker), return `Pending` or `Ready(output)`. You rarely implement `Future` by hand for application code; `async` syntax generates the state machine. Understanding poll explains why holding a standard library blocking lock across an `.await` is dangerous, and why futures must not be left half-polled in invalid states.

### 3. Async is not multithreaded by itself

Writing `async fn` does **not** spawn OS threads and does **not** parallelize CPU work. A future runs only when an **executor** polls it. A single-threaded executor can interleave many futures on one thread (concurrency of waits). Multi-threaded executors can poll futures on a pool of threads (parallelism of ready tasks)—that is a **runtime** property, not an automatic consequence of the `async` keyword.

CPU-bound loops inside `async fn` without await points starve other tasks on that worker. Use blocking thread pools, `spawn_blocking`-style APIs, or ordinary threads for heavy compute.

### 4. You need a runtime

The language and `std` provide the **Future** abstraction and some building blocks; they do not ship a full production async I/O stack in the same way as “just run my `async fn` main.” Ecosystems provide **runtimes** that include:

- An **executor** (poll tasks to completion)
- A **reactor** / I/O driver (sockets, timers, readiness)
- Task spawning, join handles, and often utilities (timeouts, intervals)

**Tokio** is a common choice in the ecosystem for network services and agents; other runtimes exist. Pick **one** primary runtime per binary/workspace when possible—mixing executors and incompatible I/O types is a frequent source of pain. This handbook does not endorse a vendor; it records that **runtime choice is an architectural decision** with dependency, feature-flag, and operational consequences.

```rust
// Pattern only — attribute and crate come from your chosen runtime
// #[runtime::main]
// async fn main() { /* ... */ }
```

### 5. Blocking in async contexts

Calling blocking `std::fs`, `std::net`, `thread::sleep`, or `Mutex::lock` that waits long on an async worker thread prevents that worker from polling other tasks. Symptoms: latency spikes, apparent “deadlocks,” timeouts under load.

Mitigations:

- Use the runtime’s **async** I/O and timer APIs
- Offload blocking work to a **blocking pool**
- Use async-aware locks when holding locks across `.await`
- Keep CPU work off the async workers or chunk it with yields

### 6. Cancellation

Dropping a future (for example leaving a `select!`-style race, or timing out) **cancels** it at the next await point boundary in practice: the state machine is dropped. Destructors run; there is no automatic “finally” beyond `Drop`. Design for:

- **Cancel-safe** state (partial progress either rolled back or explicitly checkpointed)
- Cleanup in guards/`Drop`, not only after the final await
- Timeouts as first-class operations, not hope that the peer resets

Cancellation is a feature (deadlines, client disconnects) and a footgun (interrupted multi-step mutations).

### 7. `Pin` at a high level

Self-referential futures generated by `async` must not be moved in memory after certain points. **`Pin`** is the type-system tool that says “this value will not move.” Application authors mostly see `Pin` in signatures and rare manual `Future` impls; you do not need to invent pinned structures for typical `async`/`await` usage. Know that **`poll` takes `Pin<&mut Self>`** so generated futures remain sound.

### 8. When to stay synchronous

Prefer ordinary threads or single-threaded sync code when:

- Work is mostly CPU-bound or a few blocking I/O calls
- A simple `Command` + files CLI has no concurrency need
- The team cost of runtime features, `Send` bounds, and cancellation design exceeds the benefit
- You would only wrap sync I/O in `async` without overlapping waits

Async shines when **many concurrent waits** (connections, timers, fan-out) must share few threads efficiently.

## 2. Advanced concepts

### 1. `Send` futures and worker threads

Multi-threaded executors often require spawned tasks to be **`Send`** so they can move across threads. Capturing `Rc`, `RefCell`, or other non-`Send` types inside a spawned task fails to compile. That error is teaching you about the runtime’s threading model—not an arbitrary annoyance.

### 2. Structured concurrency habits

Unbounded `spawn` without tracking join handles creates detached work that outlives requests. Prefer scoped join patterns, join sets, or explicit task budgets so shutdown drains or cancels work predictably.

### 3. Timers and time sources

Async timeouts depend on the runtime’s timer driver. Testing with paused/auto-advancing time (where the runtime supports it) prevents flaky sleep-based tests. Wall-clock jumps still affect `SystemTime`-based logic even in async apps.

### 4. Compatibility and ecosystem choice

Libraries often commit to a runtime’s I/O types (`TcpStream` from that ecosystem, not `std::net`). Abstracting behind traits helps tests but has cost. Document the chosen runtime and MSRV/feature flags in the crate README for operators.

### 5. Edition and language notes

`async`/`await` is stable across modern editions; Edition **2018** introduced the syntax widely used today. Newer editions refine other language defaults; async semantics remain “future + executor.” Nightly-only experiments are out of scope for production handbooks—pin **stable** for services.

### 6. Observability pitfalls

Task dumps, blocked-runtime metrics, and “async stack” tooling are runtime-specific. Plan the same SRE questions as for thread pools: who is waiting, on what, and is the executor saturated?

## 3. Applications and use cases

### Software engineering

- Adopt async at the **edges** (accept loop, outbound clients) and keep pure domain logic sync when possible.
- Bound concurrency (semaphores, join pools); do not spawn unbounded tasks per input line.
- Make cancellation and partial failure part of the API contract for multi-step flows.

### Security

- Timeouts on all external awaits reduce resource-exhaustion DoS from stuck peers.
- AuthN/AuthZ logic should not assume a task runs to completion—cancellation can interrupt privilege-sensitive sequences if not designed carefully.

### Reliability and operations

- Graceful shutdown: stop accepting, cancel or drain tasks, flush telemetry.
- Separate metrics for queue depth, worker utilization, and blocking-pool saturation.
- Document the runtime in runbooks; upgrades can change scheduler behavior.

### Performance

- Measure before converting sync services wholesale to async.
- Avoid holding locks across `.await`.
- Watch allocation rates of large futures; box large futures when type erasure or stack size requires it.

### Staff-level review checklist

- A named **runtime** is chosen and consistent across the binary; mixing is justified or absent.
- No blocking `std` I/O or long `std::sync::Mutex` waits on async workers without offload.
- Spawned tasks are tracked for shutdown; fire-and-forget is intentional and bounded.
- Timeouts exist on external I/O; cancellation behavior for multi-step writes is defined.
- `Send` bounds match the executor; non-`Send` data stays on single-threaded paths.
- CPU-heavy work is not disguised as async without await/offload strategy.
- Sync remains an option for CLIs and simple agents—async is not a style tax.
