# Supply chain: SBOM, signing, and provenance

[← Back to CI/CD](./README.md)

Shipping fast is useless if you cannot say **what** you shipped and **whether it was tampered with**. This file covers how SBOM, signing, and provenance fit in the delivery pipeline.

Gate placement overview: [Security/4_Security_Gate_Chain.md](../Security/4_Security_Gate_Chain.md). Artifacts: [4](./4_Artifacts_And_Registries.md).

## Three related artifacts (do not conflate)

| Artifact | Answers | Notes |
|----------|---------|--------|
| **SBOM** | What components are *inside* this build? | Inventory (SPDX, CycloneDX, …) |
| **Signature** | Was this artifact produced/approved by a trusted identity? | Integrity + authenticity of the bits (or attestation) |
| **Provenance** | *How* was it built (source, recipe, builder)? | SLSA Build track; often an in-toto attestation |

SLSA FAQ: SBOMs and provenance operate at different abstraction levels — both useful; provenance does not replace an SBOM and vice versa.

## SBOM basics

Generate an SBOM from the image/filesystem you will ship, store it with the release, and scan it.

Common open tooling (Anchore OSS):

- **Syft** — generate SBOMs (SPDX, CycloneDX, Syft JSON, …)  
- **Grype** — vulnerability scan of images **or** existing SBOMs  

Standards you will see in policy docs: **SPDX** (ISO/IEC 5962) and **CycloneDX** (OWASP).

```bash
# Illustrative — pin tool versions in real pipelines
syft packages registry:"$IMAGE@$DIGEST" -o spdx-json=sbom.spdx.json
grype sbom:sbom.spdx.json --fail-on high
```

Image scan in this handbook: [Security/Trivy](../Security/Trivy/README.md) (another scanner; same *job*).

## Signing and Sigstore / Cosign

**Sigstore** provides a widely used path for signing software artifacts with **short-lived certificates** bound to OIDC identities (e.g. CI workflow identity), plus a transparency log (**Rekor**). **Cosign** is the common CLI for signing/verifying container images and attestations, typically storing signatures/attestations alongside the image in the OCI registry.

Durable practice:

- Prefer **keyless/OIDC** signing from CI over long-lived cosign private keys in secrets.  
- **Verify at deploy** (admission policy, GitOps verify, or deploy job) — signing without verification is theater.  

Cosign historically supported SBOM “attachments”; project guidance moved to **attestations** (in-toto) rather than deprecated attachment APIs — prefer `cosign attest` / verify-attestation style flows in current docs.

## SLSA Build levels

From the SLSA specification **Build track** (stable L0–L3 framing in v1.0+; see current [v1.2 build-track basics](https://slsa.dev/spec/v1.2/build-track-basics)):

| Level | Focus (simplified) |
|-------|--------------------|
| **Build L0** | No guarantees |
| **Build L1** | Provenance exists (documents how it was built; forgeable if unchecked) |
| **Build L2** | Provenance **signed**, generated by a **hosted build service** |
| **Build L3** | **Hardened** build service (stronger resistance to tampering *during* build) |

Levels describe increasing guarantees. Meeting a level means satisfying that level’s requirements in the SLSA spec — use them to plan build-platform and provenance work.

Provenance commonly travels as **in-toto** attestations; SLSA defines *what* must be trustworthy for a level; in-toto is a vehicle for the statements (per SLSA FAQ).

## Where this sits in the pipeline

```text
build → test → SBOM + vuln scan → sign / attest provenance
     → publish digest → (policy: reject unsigned / high CVE)
     → deploy job or GitOps admits only verified digests
```

Policy examples (organizational, not universal law):

- Reject unsigned images in prod clusters  
- Reject critical CVEs above a threshold unless exception recorded  
- Require provenance from *your* builder identity  

## End-to-end mental model

```text
1. CI builds image → digest D
2. Syft/Grype (or Trivy) on D
3. Cosign signs D / attests SBOM + SLSA provenance (OIDC)
4. Registry holds D + signatures/attestations
5. Deploy verifies signature + policy, then runs D
```

## Pitfalls

| Pitfall | Better |
|---------|--------|
| SBOM generated from source tree, deploy different image | SBOM the **exact digest** you ship |
| Long-lived signing keys in CI secrets | Sigstore OIDC / short-lived certs |
| Sign but never verify | Admission / verify step in CD |
| Stopping at provenance alone | Also run vuln management, least privilege, and dependency hygiene |
| Cosign SBOM attachments only | Prefer attestations per current Cosign guidance |
